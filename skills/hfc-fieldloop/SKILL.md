# HFC FieldLoop (drop-in project skill — Claude Code)

Copy this folder anywhere as **`.claude/skills/hfc-fieldloop/`** (Claude Code discovers skills there), then configure **`config.json`** at this skill's root with four directories: **Input Data Directory** (survey microdata), **Media Folder Directory** (optional — audio/image attachments; reserved for future use, no check currently reads it), **HFC Output Directory** (a OneDrive-synced folder for the shared `issue_tracking.xlsx`), and **Code Output Directory** (a git working copy the user manages themselves — World Bank practice prefers versioned code/config output; this skill only ever writes plain files there, never runs git). There is no "survey project root" concept — the skill never searches for data, and the built product is decoupled from wherever the raw data lives. Product docs: `README.md`, skill tree map: `hfc/structure.html` (generated), deps: `install.R`.

Supporting files resolve via `${CLAUDE_SKILL_DIR}` (this skill directory); every script reads its paths from `config.json`, not from CLI arguments:

```bash
Rscript .claude/skills/hfc-fieldloop/scripts/run_setup_build.R
Rscript "${CLAUDE_SKILL_DIR}/scripts/run_setup_build.R"
```

**Built product** (`config/`, `instruments/`, `outputs/`, `code/` — with `code/checks/` and `code/resolutions/`) always lands under **`hfc/`** inside the configured Code Output Directory. `issue_tracking.xlsx` itself lives entirely in the configured HFC Output Directory (required — see A0), not under `hfc/`. `hfc/structure.html` and the report open together at the very end (A4), for the final Review & Approve gate — see Pipeline A below.

Two pipelines — choose by the user's prompt (see `references/prompts.md`):

| Intent | Trigger examples | What you do |
|---|---|---|
| **A. Setup** | "Run HFC FieldLoop" | Discover → 4 gates (config reuse, data found, instructions, completion signal) → everything else decided silently → build → open report + approve → push to tracking sheet |
| **B. Post-feedback** | "Process HFC feedback" | Clone → list Open+Comment rows → per row: read + write fix code → apply (single pass) → merge back → confirm → commit |

## Interactive confirms (AskUserQuestion) — guess first, correct if wrong

**Required.** Read and follow `references/interaction.md`.

The core pattern for every confirm in this skill: **the agent always states its own best guess first, in plain language, then gives the user a fast way to accept or correct it** — one atomic fact per tab, minimal text, packed into as few windows as possible. Two structural terms used throughout this doc:

- **Window** = one `AskUserQuestion` tool call.
- **Tab** = one `question` entry inside that call, covering exactly ONE fact/guess. A window can hold up to 4 tabs, all shown to the user together as a single interaction.

**Standard tab template — use this for every tab:**
> *[Guess + how it's used. ≤2 sentences, no em-dashes.]*
> Option 1: starts with "Looks good" (e.g. "Looks good!", "Looks good, continue!")
> Option 2: contextual to the tab's subject, not literally "Needs correction" (e.g. "The list needs edits", "A mapping is swapped", "The threshold is wrong") — "(I will type in Other)" unless a named 3rd/4th option already covers the correction path

Rules:

- One fact per tab. Never bundle multiple independent guesses (e.g. duration column + SD rule + work hours) into a single tab's text — that was the old design and it's been reverted.
- Sentence 1 leads with the concrete artifact (real path, real column name). Sentence 2 states only what's needed to judge the guess, plus any real downstream effect on other checks (e.g. "every other check runs on that subset only") — never leave a consequential effect implicit.
- Options aren't always the generic "Looks good!"/correction pair. When a rule has a natural partial-accept split, or an obvious alternate mode, enumerate those as real, named options (up to 4) instead of routing everything through free-text Other.
- List full item sets explicitly in a tab's own text (e.g. every variable name, not "and 5 more") — only the *options* array is capped at 4, the description text isn't.
- Timezones are always stated as abbreviation + city/country + UTC offset (e.g. "CAT (Blantyre, Malawi, UTC+2:00)"), never a bare IANA name.
- **Pack windows to capacity.** Backfill spare tab slots in an earlier window rather than opening a new one for 1-2 leftover facts — minimizing window count matters more than keeping tabs topically pure. Only a genuine data dependency (a tab whose content requires output that doesn't exist until a prior tab's answer is acted on) justifies a new window. See the Gate map in `references/interaction.md` for the current window-by-window packing.
- Fallback only if AskUserQuestion is unavailable: state the guesses as a numbered list in chat and ask the user to reply "looks good" or describe corrections — still not a typed mega-string like `M1=Y M2=N`.

## Operating principles

1. **Only 5 gates in Pipeline A: Config reuse, Data found, Instructions, Completion Signal (all A1), and Review & Approve (A4, final).** Everything else the agent decides is applied silently, with no `AskUserQuestion` and no chat narration — no phase between the 4 early gates and the final one waits for confirmation. What's silently decided still isn't final until the user approves at Review & Approve: the live `issue_tracking.xlsx` is never written before that.
2. Never mutate original microdata in the configured Input Data Directory — agent-authored fixes write to `<sibling of Input Data Directory>/intermediate/<stem>.<ext>` instead (one evolving file, never inside the git-tracked Code Output Directory).
3. **Guess first, correct if wrong** (see Interactive confirms above) — every gate that does fire states the agent's own best guess and gives one free-text correction option, never a long menu of choices. Applies to the 5 gates in principle 1, and to every tab in "Deep Review tabs" (A2) if the user asks for a walkthrough.
4. Feedback: **one shared file**, `issue_tracking.xlsx` — edited collaboratively by the agent, the RA, and the field team on the same file (Comment/Corrections/Status all live in the same sheet; no separate audit twin). OneDrive is **required** (no local fallback in the product — see A0): once `config.json`'s **HFC Output Directory** points at a folder the OneDrive desktop app is syncing, that folder is the **sole store** — every read/write is plain file I/O against it, and OneDrive's own sync client (not this skill) propagates changes to the cloud, so there is never a separate local-only copy. Two dated-snapshot subfolders live alongside it, inside the same synced folder: `intermediate/<YYYYMMDD>_issue_tracking.xlsx` (one per setup-build run) and `resolutions/<YYYYMMDD>_issues_resolution.xlsx` (the agent's working clone during a "Process HFC feedback" pass) — see `references/issue_tracking_schema.md`. All four directories live in the skill's own `config.json` — the only file that matters, edited directly, no per-project override, no auth step or secrets in this package. The OneDrive folder is then shared manually (by whoever owns it) with collaborators via OneDrive's "Specific people" sharing UI.
5. Open `<MMDD>_HFCs.html` exactly once per pipeline pass, with `utils::browseURL()` (or OS `open`) — only after the Summary narrative (and, in Pipeline A, the README) are already folded in. Never at a preview/first build: opening an incomplete report and then silently rewriting the file underneath that open tab is confusing, not helpful.
6. **Must** write `hfc/config/modules.yaml` + `hfc/config/role_map.yaml` from the user's **confirmed** (guessed-then-corrected) options **before** calling the builder; also write `hfc/config/module_notes.yaml` whenever a custom check was confirmed, and `role_map.yaml`'s `important_vars` from the confirmed shortlist.
7. M9 (Field Request) has no built-in checks and defaults to **off / empty** — every M9 finding comes from a custom check the agent writes for this survey's specific content, driven entirely by what the user describes in the Instructions tab (A1, Setup window). A check tagging its rows `category = "field_request"` renders in M9's own Info-labeled section; every other custom-check category renders in the adjacent "Other" section instead.
8. **Specific-check requests are handled every run, from the Instructions tab (A1)** — there's no dedicated Field Request tab anymore. Read the Instructions answer for anything resembling a requested check every time; match it to a standard module first, else author an M9 custom check silently. Nothing said about checks → M9 stays off/empty, same effective default as before.
9. Draft `<Code Output Directory>/README.md` from `assets/README_template.md` automatically — no confirmation needed, it's just documentation. Point to `references/ai_use.md`.
10. **M13 media, redesigned:** the ONLY thing to flag is a media-indicating column that is completely empty across every surveyed row (a form/coding problem — the field isn't showing up in the enumerator's app, or the question is misconfigured) — never per-row file hygiene, and no on-disk file access at all. Which columns indicate media presence (audio/image filename columns, plus any qualitative open-text columns the agent itself identifies) is decided silently (A2 step 5) — only shown back to the user under a Deep Review walkthrough. Never put filename cols under M14.
11. **Completion is redefined:** it means whether all PLANNED surveys were conducted, not whether a started survey finished. The agent detects a completion signal — preferring a real gate/eligibility question read from the instrument, else a target/roster file, else a primary/secondary sample column — and confirms it via the Completion Signal gate (A1) — only when a signal is actually found; if none is found, M1 falls back to its original row-missingness heuristic and nothing else changes. Once confirmed, if a "gating" (or legacy "status") signal shows some rows were not completed, EVERY other check module (M2–M14) runs only on the completed/surveyed subset — incomplete rows are filtered out before any other check sees them. M1 itself always sees the full picture (the complete dataset, or the roster/target list).
12. **Grouping defaults to Treatment/Control**, not geography — M1's completion-by-group stats table groups by a Treatment/Control column, identified by the agent's own judgment (A2 step 2), first. Geography is only used when no Treatment/Control column exists, or the user explicitly opts in to it alongside Treatment/Control (default: declined — ask about this only when a Treatment/Control column was actually found).
13. **Redundant/near-duplicate variables** (e.g. `treat` vs. `treat_ext`, `age` vs. `age_calc`): always silently keep the single most reasonable one in every shortlist you propose — never present both as if independently meaningful, and never ask the user to pick between them.
14. **Country inference must come from geography in the data** (district/region/village/site names, or a GPS bounding box), never from the input folder's name/basename — that's a report-title convenience only, not a location signal.
15. **Be careful about assent vs. consent** — they are different concepts (assent = the child/minor's own agreement; consent = the parent/guardian's, or an adult respondent's own). Decided silently (A2 step 5), naming which column maps to which concept — under Deep Review, its own tab, never bundled with anything else.
16. **Nested questions:** when form `relevant` says a child item is skipped, do not flag blanks as missing.
17. All product code/artifacts under **`hfc/`**.
18. **Report-wide sort:** every issues table sorts by date (most recent first), then enumerator, then unique ID — module sections stay in their fixed order (M1..M14), but there is no severity/worst-first ordering within a table. Dateless aggregate-level findings (group/enumerator-level, never tied to one day) sort last within their module. Every row-level finding matching the confirmed last date also appears in the dedicated Last Day tab (aggregate findings never can, since they have no date).
19. **Never ask a tab whose subject a prior answer already resolved.** Applies to the 4 early gates, and to a Deep Review walkthrough: check whether a topic is already settled — by A1's Instructions answer (free text or a hand-edited, non-blank value in `modules.yaml`/`role_map.yaml`) — before presenting it, even under "Walk me through all modules." If resolved, skip that tab and state the fact once in chat instead of re-asking. Concrete example: declining GPS checks entirely (`M10.on: no`) skips the Map focus tab too, since there's no map to focus without GPS data — `write_html_report()` ties the map's rendering to `M10.on`. (GPS Map itself never needs a threshold tab — it's a pure visualization by default, see Operating Principle 21.) If skipping drops a Deep Review window to ≤1 remaining tab, backfill into a neighboring window rather than firing a near-empty one for a single leftover fact.
20. **GPS Map (M10) never flags a point by default — visualization only.** Plots every submission with a valid coordinate; no distance threshold, no flagged points, no findings table, regardless of sector or project. Do not propose a distance-threshold tab as part of the standard setup flow. The old median-reference distance-outlier logic still exists, but only as an advanced opt-in (`modules$M10$advanced_distance_flag$on`) — surface it only if the user's own Instructions specifically ask for GPS-based flagging.
21. **Missingness (M7) is descriptive only by default — never flags an enumerator or a variable as an issue**, on either the question or the enumerator level; it's a reference table, not an issue list. The old enumerator-level flagging logic still exists as an advanced opt-in (`modules$M7$advanced_enum_flag$on`) — surface it only if the user's own Instructions specifically ask for missingness to be flagged, not just reported.

## Pipeline A — Setup

### A0. Config pre-flight (mandatory, every run)

There is no "survey project root" and no local-only mode — everything is driven by `skills/hfc-fieldloop/config.json`, naming four directories: **Input Data Directory**, **Media Folder Directory** (optional), **HFC Output Directory**, **Code Output Directory** (Input Data Directory, HFC Output Directory, Code Output Directory are required). Before proceeding to A0b/A1, verify `config.json` is fully configured — real paths, not the shipped `<...>` placeholders (this is exactly what `require_fieldloop_config_ready()` in `scripts/lib/issue_store.R` checks — every CLI script in this skill calls it automatically and `stop()`s with the same instructions below, naming the specific missing field, so this gate is also enforced in code, not just in this doc).

- **If it's already fully configured:** say so briefly in chat (name the three configured directories) and continue to A0b — no AskUserQuestion needed, there's no choice to make.
- **If any required field is missing or still a placeholder:** stop here. Tell the user, in this order: (1) run `Rscript <skill_dir>/install.R` if packages might be missing, (2) make sure the OneDrive desktop app is installed and signed in on this machine, and note the local folder it syncs to, (3) edit `<skill_dir>/config.json` — set Input Data Directory, HFC Output Directory, and Code Output Directory to real absolute paths (Media Folder Directory optional) — this is skill-level config, applies to every run using this skill copy. Do not proceed with Pipeline A or B until they confirm this is done and the pre-flight succeeds.

### A0b. Config-reuse gate (Window: Config reuse — conditional)

Immediately after the config pre-flight passes, check whether `hfc/config/role_map.yaml` **and** `hfc/config/modules.yaml` already exist under the configured Code Output Directory (a prior run). If neither exists, skip straight to A1 — nothing to reuse yet, no window shown. If they exist, one tab, three real options (no generic Other needed, these three cover it):

> *Found a saved setup from a prior run. Rebuild using it as-is?*
> - "Yes, reuse and rebuild (recommended)" — proceed straight to A4 build with the saved configs; skip A1 and A2 entirely (the existing reload logic in `run_setup_build.R` already handles this).
> - "No, start fresh" — delete `hfc/config/role_map.yaml` and `hfc/config/modules.yaml` (only those two files), then run A1–A4 normally as a first-ever setup.
> - "Let me edit the config files first" — state the paths (`hfc/config/role_map.yaml`, `hfc/config/modules.yaml`), wait for the user to confirm they're done, then proceed straight to A4 build; the existing reload logic picks up their hand-edited values automatically.

### A1. Discover, gather instructions, detect completion signal (Windows: Setup — 2 tabs, always [Gates 2-3]; Completion Signal — up to 1 tab, conditional [Gate 4])

**Only four gates fire during a normal setup run: Config reuse (A0b), Data found, Instructions (both below), and Completion Signal (end of this section).** Everything else this doc used to ask about — Entity, Country, Daily target, Replacement sample, and every module-confirmation window in A2 — is now decided **silently**: the agent applies its own best guess, writes it directly to `role_map.yaml`/`modules.yaml`, and moves on, with no `AskUserQuestion` call and no chat narration. The exact guess logic for each of those is unchanged from before — it's collected in **"Deep Review tabs"** at the end of A2, replayed only if the user asks to "Walk me through all modules" at A4's final Review & Approve gate.

**Reading order, once data is found but not yet deeply read: Instructions → project description (`context_doc`) → survey instrument/form → the microdata itself.** Each step below is informed by everything resolved before it, so the most inference-heavy step — loading and profiling the actual data — runs last and skips whatever's already known instead of duplicating it.

1. Run discovery in the configured Input Data Directory only — no searching elsewhere, but including any nested subfolders (`discover_project()`). This surfaces the data/form paths, a `roster_candidate` (a second file that looks like a target/planned-sample list, used by completion-signal detection in step 8), and a `context_doc` (a project description / Pre-Analysis Plan document — pdf/doc/docx/txt/md). This is a filename-pattern shortlist only, not a trusted classification — form and `context_doc` get their content verified in step 6 (open and read them; if the content doesn't actually match the guessed role, e.g. a "form" with no survey-instrument-like sheets, re-classify rather than proceeding on the filename match). For `roster_candidate` specifically, open it before relying on it in step 8b — confirm it actually looks like a planned/target sample list (respondent IDs + a target-vs-actual or primary/secondary-style column), not a second data extract that merely sorted second by file size.
2. **If nothing is found:** tell the user to drop files into the configured Input Data Directory, then try again. Do not proceed without data.
3. Form optional: proceed data-only; note M9 / M3 / nested logic weaker.
4. **Write a blank `hfc/config/modules.yaml`** immediately:
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/preview_modules.R --blank
   ```
   Writes a commented draft with every M1–M14 block present but unfilled (just its `desc:`/comment header) — no data dependency, safe to run before any role profiling. Its real path is stated in the Instructions tab below, inviting the user to pre-fill anything they already know (module on/off, thresholds, variable lists) directly in the file instead of waiting to be asked.
5. **Window "Setup" — 2 tabs, fires immediately, before any role profiling:**
   - **Data found** (Gate 2): sentence 1 states the real paths found (data file, form if any, and project description/PAP document if found); sentence 2 states row count, column count, and collection date range.
   - **Instructions** (Gate 3): *"Any specific instructions for this data or this HFC check session? This can be anything I should know before diving in, e.g. disabling checks, naming the country, or specific checks you'd like run."* States the blank `modules.yaml`'s real path (from step 4) and invites pre-filling it directly, or leaving it for the agent to guide the rest of setup. Options: `"All good!"` / `Other`.
6. **Apply the Instructions answer before doing anything else:**
   - Interpret the free text as concrete facts/directives (e.g. "no GPS checks" → `M10.on: no`; a stated country → skip country inference and use it directly), and re-read `modules.yaml` for any hand-edited, non-blank values. Both become **already-resolved facts** — every silent decision from here on checks against them first instead of re-guessing (Operating Principle 19).
   - **Specific check requests:** match each one against the standard M1–M14 mechanics first (e.g. "flag surveys under 10 minutes" → set M4's threshold; "check for outliers on income" → add `income` to M6's variable list). Anything that doesn't map onto a standard check becomes an M9 Field Request custom check — design a check name, write `hfc/code/checks/<name>.R`, register it under M9/`custom`, and write its ≤3-sentence plain-English description to `hfc/config/module_notes.yaml` (`custom.<name>.label`/`.description`), same authoring mechanism as before, just triggered here and done silently (no separate confirm). A genuine field/daily-reconciliation check tags its rows `category = "field_request"` so it renders in M9's own Info-labeled table; any other custom category renders in the adjacent "Other" section instead. If Instructions says nothing about specific checks, M9 stays off/empty — same as the old "No additional checks" default, just without a dedicated tab asking about it.
7. **Now** read remaining context, in order, each informed by everything resolved in step 6:
   a. **`context_doc`, if found** — the Read tool handles PDF and text/markdown directly. If it's a `.docx`, run `Rscript <skill_dir>/scripts/lib/docx_text.R "<path>"` first (prints the path to a plain-text extraction, no new dependency — it's just an unzipped `word/document.xml`) and `Read` that instead of the binary file. Legacy binary `.doc` (pre-2007, not a zip container) can't be parsed this way — for that one format only, say so briefly in chat and ask the user to export it as `.docx` or PDF instead, and move on without blocking setup. Treat its contents as **background context only** — survey purpose, design, treatment arms, target sample/completion, key outcome variables, timeline. It is never itself a data source: never parse findings or role fields out of it mechanically, and never let it silently override what the actual microdata shows — if the two conflict, trust the data and flag the discrepancy in chat. If multiple candidate documents were found with no clear name match, don't guess — name them all in chat and ask which one, in the same message as the Instructions tab's summary (no separate tab).
   b. **The survey instrument/form, if found** — run `Rscript <skill_dir>/scripts/lib/form_text.R "<form_path>"` first (prints the path to a plain-text dump of **every sheet** in the workbook, not just the first) and `Read` that dump, never the raw `.xlsx` directly — a real SurveyCTO/XLSForm instrument routinely spreads what's needed across several sheets (`survey`: question name/type/label/relevant/required; `choices`: the value labels behind every `select_one`/`select_multiple` question, e.g. what code `1` vs `2` actually means; `settings`: form title/id/version), and reading only the first sheet would silently miss the `choices`/`settings` content entirely. Covers skip-logic (`relevant`), question structure, and choice-code meanings; informs M9/M3/nested-logic judgment as well as gate-pass-value and sentinel-code interpretation.
   c. **The microdata itself, loaded and profiled last** (`profile_roles()`) — every one of the following is decided **silently** (write directly to `role_map.yaml`, no confirmation, no chat narration — same guess logic as before, now just applied instead of asked; see Deep Review at the end of A2 to replay any of it on request), lightened or skipped wherever step 6 already resolved it:
      - **Entity ID**: `shortlist_entity_ids()`'s top candidate.
      - **Entity Label**: a Title-Case guess for what to call the entity (e.g. "Household" for a column named `hhld_id`) — used everywhere the entity is displayed: the HTML report's findings tables *and* the xlsx/csv issue-tracking export.
      - **Duplicate-check key**: auto-resolved — Entity ID alone if already 100% unique in the raw data, else Entity ID + the top `detect_duplicate_key_candidates()` hit.
      - **Media-indicating columns**: `detect_media_vars()` for audio/image filename columns, plus any qualitative/open-text columns the agent itself identifies as capturing qualitative data.
      - **De-identification defaults (fixed, never guessed or asked):** HFC data is de-identified by default — the entity's real name is never available, but enumerator names usually are. `profile_roles()` sets `roles$entity_display = "id"` (Entity always shows the raw ID), `roles$enumerator_display = "name"` and `roles$group_display = "name"` (Enumerator/Group show the name when one exists, else the ID) — applied everywhere (HTML report findings tables *and* their descriptive stats tables, `issue_tracking.xlsx`/`issues.csv`) via `resolve_display_vec()` (`scripts/lib/utils.R`). Only change one if a user **explicitly** asks (e.g. "this data isn't anonymized, show respondent names" or "show enumerator IDs instead"): edit the matching field directly in `hfc/config/role_map.yaml` and rebuild — never guess or proactively offer this.
8. **Country**: skip entirely if step 6 already stated it. Otherwise, if an explicit country-name/code column exists (`shortlist_country_columns()`), use it directly and resolve its timezone(s) via `resolve_country_timezone_column()` (`scripts/lib/geo_timezone.R`). If not, read the sampled values from `shortlist_geography_signal_cols()` (district/region/village/site-name-like columns, plus a GPS bounding box if coordinates exist) and use your own general-knowledge judgment to state a best-guess country — **never infer this from the input folder's name/basename**, that's a report-title convenience only. Resolve the guessed country's timezone via `resolve_country_timezone()` — timezones are always abbreviation + city/country + UTC offset (e.g. "CAT (Blantyre, Malawi, UTC+2:00)"), never a bare IANA name. Apply silently — write `country`/`country_col`/`timezone` directly to `role_map.yaml`, no confirmation.
9. **Detect the completion signal.** Gating (a real screening/eligibility question from the instrument) is the primary, preferred signal — reading the actual instrument is more reliable than pattern-matching a column name. Detection order:
   a. **gating (preferred)** — read the instrument's `type`/`label`/`relevant` columns like an analyst would, looking for root-level screening questions whose failure skips most/all of the rest of the survey (household presence, consent, age/eligibility checks). As a supporting signal, not a replacement for judgment, compute `gate_fanout_counts(form_map)` (`scripts/lib/form_logic.R`) — how many other questions' `relevant` expressions name each column as a parent, via the existing `relevant_parents()`; a high count is a strong hint of a true gate. Order confirmed gates by where they appear in the form (earliest first — later gates are only reached if earlier ones pass).
   b. **roster** — the `roster_candidate` from step 1: a second file that looks like a target/planned-sample list. Only relevant when no credible gate was found. When roster wins, completion-by-strata (village, health facility, Treatment/Control, etc.) reports the roster's own **target sample size** as the denominator — percent of the planned sample actually surveyed, not percent of submitted rows — so also check whether `modules$M1$group_vars` (the strata column(s) already detected in the survey data) exist by the same name in the roster file. If a strata column's name differs there (e.g. survey data has `village`, the roster has `village_name`), resolve the match by column-name similarity or by comparing raw values, and state it in the Completion Signal tab below — silent when the names already match (the common case).
   c. **primary_secondary** — a column within the surveyed data marking each row Primary or Secondary sample (no separate roster). Only relevant when no credible gate was found.
   If no gate, roster, or primary/secondary signal is found at all, there's nothing to confirm — skip the Completion Signal window entirely, and M1 falls back to its original row-missingness heuristic.
   d. **Replacement-sample structure — independent of a/b/c above, checked whenever a roster file exists at all** (even alongside a `gating` signal): inspect the roster's own columns for a Primary/Secondary-or-Replacement status column, a numeric position-in-the-replacement-queue column (only meaningful on non-primary rows), and a group column (e.g. health facility or village — matched by raw value against `roles$group` in the survey data). This is agent judgment, the same posture as reading the instrument for gates in step 9a — read the actual column names/values, don't guess from a fixed name list. Blank/not-found on any of the three skips the whole feature.
10. **Window "Completion Signal" — up to 1 tab, fires right after step 9, whenever any signal (gating, roster, or primary_secondary) was detected — Gate 4:**
    - If gating: states the guessed gate question(s) in form order with their labels (e.g. `hh_present` "Household present?", `consent` "Consents to interview?"), and that a failing answer's value becomes the non-completion "Reason" for that respondent — the first failed gate wins, since later gates were never reached. If a gate was clearly added to the form partway through data collection (e.g. it's absent from earlier submissions entirely), state the guessed `gate_min_date` exempting submissions before then from failing it. If one gate can legitimately be revisited after an earlier one misfires (typically consent), state it as the guessed `governing_gate`.
    - If roster/primary_secondary (no gate): state that signal instead (name the file/column, the downstream filtering effect) — when roster wins and step 9b needed to resolve a strata-column name mismatch, also state that mapping (e.g. "the roster's `village_name` column matches the survey data's `village`").
    - If more than one signal type is genuinely available at once, do NOT silently pick — name the conflict explicitly and flag it as needing a closer look.
    - Options: `"Looks good!"` / `"The list needs edits (I will type in Other)"`.
    - Skipped entirely (no tab) only when no signal at all was found.
    - **Daily target** and **Replacement sample** (guessed alongside the signal above): decided silently, same guess logic as before (daily target: the overall median enumerator-day submission count, as a starting proposal; replacement sample: the roster's status/rank/group columns, when step 9d found them) — written directly to `modules.yaml`'s `M1` block, no confirmation.
11. Persist everything (confirmed via the tabs above, or decided silently) to `hfc/config/role_map.yaml`: `entity_id`, `entity_id_sep`, `entity_label`, `dup_key_extra`, `country_mode`, `country`/`country_col`/`country_timezone_map`, `timezone`, `qualitative_text_cols`, `completion_primary_signal` (now typically `"gating"`), `completion_roster_candidate`, `completion_roster_key_col`, `completion_roster_group_map` (only the entries step 9b actually needed to resolve — blank/omitted whenever strata column names already match), `completion_primary_secondary_col`, `completion_primary_value`, `context_doc_path` (from step 7a, so a rebuild doesn't need to re-discover it). Do not write `completion_status_col`/`completion_status_complete_values` fresh — those fields are superseded by gating, kept readable only for backward compatibility with a config from before this change. Write to `hfc/config/modules.yaml`'s `M1` block: `completion_signal`, `gate_cols` (ordered), `gate_pass_values`, `gate_labels`, `gate_min_date`, `governing_gate`, `daily_target_per_enum`, `replacement_status_col`, `replacement_primary_values`, `replacement_rank_col`, `replacement_group_col`.

1. Read `references/check_modules.md` and `references/interaction.md`.
2. Profile columns (names/types/labels only — no PII row dumps) and compute proposed defaults for every module (`default_modules()`), now using the roles confirmed in A1. **Identify the Treatment/Control column yourself**, from real column names and value distributions (e.g. `arm`/`condition`/`assignment`-like columns with 2-3 distinct values reading as Treatment/Control/T/C/1/0) — naming conventions vary too much by sector to pattern-match reliably, so read the actual data rather than trusting a fixed name list. Apply silently — write `role_map.yaml`'s `treatment_control_col` directly (persisted in step 7 below). Fall back to geography only when no Treatment/Control column exists.
3. **Write the informed module config:**
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/preview_modules.R
   ```
   Merges fresh, role-informed guesses (on/off, thresholds, variables) with whatever's already sitting in `hfc/config/modules.yaml` from A1's blank draft (step 4) — any field the user hand-filled there wins; everything else gets a real guess (`merge_prefilled_modules()`, `scripts/lib/check_modules_preview.R`). Rewrites the same file in place, one module per commented block — a real file on disk the user can hand-edit at any time. This IS the file that ends up governing the actual build; corrections (from a "Walk me through all modules" pass, or a hand-edit the user mentions at the final gate) just edit this same file in place.
4. **Important variables shortlist (unified for M6/M8/M11/M7) — mandatory, every run:** propose up to 10 variables using your own judgment about what's contextually important to this survey — read column names/labels/content, informed by (not limited to) the profile's numeric/ordinal candidate pools, not driven by numeric-ness alone. When two or more candidates are near-duplicates of each other (e.g. `treat` vs. `treat_ext`), silently keep only the single most reasonable one — never present both. **Scan these variables' value distributions yourself for likely sentinel/missing codes** (99, -99, -9999, … appearing disproportionately outside the variable's normal range). When the form is available, cross-check each candidate against its question text/choice labels (`form_text.R`'s dump) rather than relying on the value pattern alone — a code the form's own choice list defines (e.g. "999 = Don't know") is a confirmed sentinel, not just a guess.
   Additionally, for M7 Missingness specifically, read through the full column list and select ~20 more variables (any type, not just numeric) you judge important for missingness reporting — broader than the unified shortlist above. Agent judgment only, write directly to `hfc/config/role_map.yaml`'s `missingness_extra_vars`. An RA who disagrees with the picks edits that file directly.
   **Never select a skip-logic-dependent (conditional) variable for the missingness pool by default** — check the parsed form's `relevant` column (`parse_form_relevance()`, `scripts/lib/form_logic.R`) for every candidate; if it has a non-blank `relevant` (it's a child of some other question), it's inherently conditional and gets excluded from both the unified shortlist and the M7 extra-vars list, even though `filter_expected_skips()` would correctly zero out the row-level denominator anyway — the point is not to propose it as a missingness check target at all. The only exception: the user explicitly asked to include that specific variable (Instructions tab) — then include it and don't second-guess the request.
5. **Apply every one of the following silently — same guess logic as always, write directly to `modules.yaml`/`role_map.yaml`, no `AskUserQuestion`, no chat narration:** duplicate key; form version + date-range mapping (only if 2+ versions detected); duration column, plus section-level timing if `roles$section_time_pairs` found any; work hours window + weekend flag; last date of data collection; GPS coordinates (only if GPS data exists); media columns; map focus; geography opt-in (declined by default whenever a Treatment/Control column exists); group label; Balance Tables groupings (declined by default unless the project genuinely looks like a randomized/multi-arm design); consent/assent/audio-consent mapping; Excel columns (always the standard `issue_tracking.xlsx` schema — never varies, see `references/issue_tracking_schema.md`). **The exact guess logic, thresholds, and tab wording for every one of these lives in "Deep Review tabs" below** — replayed only if the user asks to "Walk me through all modules" at A4's final Review & Approve gate.
6. **Generate clean variable labels (`var_labels`) — mandatory, every run, agent judgment only, no `AskUserQuestion` confirmation** (same posture as step 4's M7 extra-vars pick): by this point every column that can actually surface in a finding or the tracking sheet is known — the unified important-variables shortlist + M7's extra missingness vars (step 4), the media columns, the assent/consent/audio columns, and the duplicate-key/form-version columns (all decided in step 5). For each, read the raw column name and its instrument question label (already available from `form_text.R`'s dump, A1 step 7b) and write a short, clean, human-readable label — neither the bare column name nor the verbatim question text (e.g. `q14_wait_time_min` + "How long did you wait to be seen, in minutes" → "Wait time (min)"). Write directly to `hfc/config/role_map.yaml`'s `var_labels: {colname: "Clean Label", ...}`. Falls back to the raw column name wherever a column has no entry (e.g. a rebuild against an older config) — never blocks a build. An RA who disagrees with a label edits the file directly, same as `missingness_extra_vars`.
7. Write every module setting decided above (silently, or via a Deep Review correction) into `hfc/config/modules.yaml` in place (its comments and every other module's settings stay untouched), then write the remaining `hfc/config/role_map.yaml` fields: `important_vars`, `missingness_extra_vars`, `var_labels`, `last_date`, `treatment_control_col`, `geo_group_col`, `geo_group_opted_in`, `map_focus`, `group_label`.

### Deep Review tabs (only if the user asks to "Walk me through all modules" — A4's final Review & Approve gate)

     - **"Walk me through all modules"** → replay every window/tab in "Deep Review tabs" (end of A2), each pre-filled with the value already computed. Apply any corrections directly to `modules.yaml`/`role_map.yaml`, redo steps 6-7 (recompute checks, redraft the summary against the corrected config), and re-ask this same gate.
     - **Free-text correction (the tool's automatic "Other")** — covers both a described fix ("the duration threshold should be 4 SD," "School 6 isn't actually low-completion") and a direct "I edited `modules.yaml`/`role_map.yaml` myself, go ahead" (re-read the files rather than trusting the prior draft). Apply whatever's needed, redo steps 6-7 (report re-opens; `hfc/structure.html` only re-opens if it changed — `first_setup` from step 1 doesn't change), and re-ask this same gate.
     - Loops until approved — none of these three paths restart the flow from A1.

## Pipeline B — Post-feedback

There is no built-in fix-classification engine. **You (the agent) read and interpret each eligible row yourself and write the fix code** — same philosophy as M9 custom checks: no fixed catalog of fix types, decide per row. Trigger: any row with `Status == Open` **and** a non-empty Comment is eligible — there is no separate Accepted gate. Everything in this pipeline operates on today's `resolutions/<date>_issues_resolution.xlsx` clone, never on `issue_tracking.xlsx` directly — the live shared file is only ever updated by the explicit merge-and-commit step at the end.

1. Create (or reuse) today's resolutions clone:
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/apply_feedback.R clone
   ```
   Copies the current `issue_tracking.xlsx` to `resolutions/<YYYYMMDD>_issues_resolution.xlsx`. A same-day second pass reuses the existing clone rather than discarding in-progress work.
2. List eligible rows:
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/apply_feedback.R list-open
   ```
   Writes `hfc/outputs/fix_candidates.csv` — one row per `Status=Open` + non-empty Comment finding in today's clone, with full context (Issue, Comment, Entity ID, Variable, Value, Issue Category, Issue ID).
3. **Window "Proceed," one tab:** *"Found `<N>` rows with a Comment and Status=Open. I'll interpret each and apply a fix in one pass per row."* — "Proceed with all `<N>` (recommended)" / "Only some of them (I will type in Other)".
4. For **each** eligible row, in turn, in a single pass — interpret the Comment, propose Corrections, apply the fix, and set Status, all at once:
   a. Read its `Issue`, `Comment`, and other fields; decide the concrete technical fix the Comment is asking for (e.g. drop the row, cap a value, recode a field), and draft the Corrections text describing what you did.
   b. Write `hfc/code/resolutions/<Issue ID, sanitized>.R` defining `fix(ds) -> ds` that implements it.
   c. Apply it:
      ```bash
      Rscript .claude/skills/hfc-fieldloop/scripts/apply_feedback.R apply --finding-id "<Issue ID>" --corrections "<what you did>"
      ```
      This loads `<sibling of Input Data Directory>/intermediate/<stem>.<ext>` if a prior fix already exists (else the original file in the Input Data Directory — never mutated), applies your `fix(ds)`, saves the result back to `<sibling of Input Data Directory>/intermediate/<stem>.<ext>` (one evolving file, so fixes accumulate), and writes the Corrections text + `Status = Resolved` into today's resolutions clone **only** — `issue_tracking.xlsx` is never touched by this step.
   d. If you can't confidently resolve a row, run `apply_feedback.R needs-review --finding-id "<Issue ID>"` instead — sets `Status = Needs Review` in the clone.
5. Once all rows are handled, fold the clone back into the live file:
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/merge_resolutions.R
   ```
   Writes `merged_issue_resolutions.xlsx` next to `issue_tracking.xlsx` — for matched Issue IDs, Status/Corrections/Correction Author come from today's clone, every other column (in case the field/RA edited something concurrently) comes from the live file untouched; unmatched live rows pass through unchanged.
6. **Window "Commit," one tab:** *"`<N>` rows Resolved, `<M>` Needs Review. This will overwrite the live shared issue_tracking.xlsx."* — "Confirm merge (recommended)" / "Wait, let me review first" (show the row-by-row diff before committing) — then commit:
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/commit_merged_issue_tracking.R merged_issue_resolutions.xlsx
   ```
7. **Rebuild the report — mandatory, every pass:**
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/rebuild_report.R
   ```
   Re-runs M1–M14 against the latest data (`<sibling of Input Data Directory>/intermediate/` if any fixes were applied, else the original file in the Input Data Directory) using the project's stored config, then drops any finding from the report whose live-tracking Status is now `Resolved`, or whose Issue ID no longer appears in `issue_tracking.xlsx` at all — display-only: the xlsx itself keeps full history unchanged, this only affects what `<MMDD>_HFCs.html` shows. Re-read `hfc/outputs/issues.csv` and redraft the Summary narrative (`hfc/config/summary_message.md`, same approach as A4 step 6) against these fresh findings, then re-run with `--open`:
   ```bash
   Rscript .claude/skills/hfc-fieldloop/scripts/rebuild_report.R --open
   ```
8. Tell the user which rows were Resolved vs. Needs Review, and that `<sibling of Input Data Directory>/intermediate/<stem>.<ext>` now holds the latest fixed data (raw unchanged).

## What not to do

- Do not write to the live `issue_tracking.xlsx` before the final Review & Approve gate (A4) is answered "All good!" — every build, first-ever or rebuild alike, produces only a pending `merged_issue_tracking.xlsx` until then.
- Do not overwrite the original microdata file.
- Do not start Pipeline A when the user clearly asked for post-feedback (and vice versa).
- Do not invent access dates, exhibit IDs, or column names that are not in the data.
- Do not skip or silently bypass the config pre-flight check (A0) — if Input Data Directory, HFC Output Directory, or Code Output Directory isn't configured or isn't reachable, stop and direct the user to `install.R` + confirming OneDrive desktop sync is running + editing `config.json`, never proceed with a build that has nowhere to write `issue_tracking.xlsx`.
- Do not show an entity's name anywhere (report or `issue_tracking.xlsx`) unless the user has explicitly set `entity_display: name` in `role_map.yaml` — Entity ID-only is the de-identification default, never overridden silently or by guess.
- Do not require monorepo gold data, `eval/`, `verify_all`, or SimUser for product runs.
- Do not use typed mega-replies (`M1=Y M2=…`) or long option menus as the primary confirmation UX — always guess first, correct if wrong (see Interactive confirms above).
- Do not silently guess the Entity ID without a wrong pick being visibly correctable — it's decided silently by default (A1), but must be nameable and fixable via Deep Review or a free-text correction at the final gate, never truly hidden.
- Do not scatter product dirs outside the Code Output Directory — everything lands under `<Code Output Directory>/hfc/`.
- Do not flag expected skip-logic blanks as missing.
- Do not ignore a specific-check request in the Instructions answer (A1) — every run, every time, match it to a standard module or author an M9 custom check; there's no separate Field Request tab to catch it later.
- Do not infer the data-collection country from the input folder's name/basename — read geography from the data itself.
- Do not let the last date of data collection go unresolved — it's decided silently (A1 step 8/A2 step 5) but must drive the Last Day tab correctly regardless.
- Do not let incomplete/non-surveyed rows leak into M2–M14 once a "status" completion signal has confirmed which rows to filter out.
- Do not run per-row file-hygiene checks for M13 — the only check is a media-indicating column that's completely empty across every surveyed row.
- Do not confuse assent and consent.
- Do not present two near-duplicate variables (e.g. `treat` vs. `treat_ext`) as if they were independently meaningful — silently keep the one most reasonable one.
- Do not hand-edit `issue_tracking.xlsx` (or any tracking-shaped file) via a raw `openxlsx`/direct-write call — use `patch_tracking_cells()` (`scripts/lib/issue_store.R`) for a targeted cell fix. A real, confirmed incident: a raw `read.xlsx()`-then-`writeData()` round trip silently rewrote the header row itself (not just cell values) to the data.frame's R-sanitized column names, un-mapping every column at once — `read_issue_tracking()` now errors loudly on this, but the safe path is to never risk it in the first place.
